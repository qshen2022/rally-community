# 让另一个球友群拥有自己的 Rally

## 最终效果

每个群自己部署一套 Rally：自己的网址、自己的管理员、自己的空数据库。两个群的报名、候补、姓名认领互不共享。源码可以共用，部署实例不能共用。

本仓库没有旧群的用户数据、真实报名名单、邮箱、访问令牌和原站点项目 ID，也没有旧仓库的提交历史。`drizzle/` 里是建表和改表的 SQL **结构**，不是数据库备份。

## 1. 准备一份新副本

使用 Node.js 24 LTS。下载仓库或克隆到新的目录，别在正在运行的 Rally 目录里操作。

```sh
npm run setup -- --owner-email owner@example.com
npm ci
npm run build
npm run db:local
npm run dev
```

把示例邮箱换成**新管理员登录 ChatGPT 时使用的邮箱**。如果用了 Apple 隐藏邮箱，以站点收到的中继邮箱为准。安装脚本只在新副本写入该邮箱的 SHA-256 值，不保存明文邮箱；它不会连接数据库，也不会发布。已有项目绑定或已有管理员配置时，它会拒绝覆盖。

本地开发使用 localhost 专用的模拟登录，目的是方便开发。它不能证明真实的 ChatGPT 授权已经完成。本地数据库在新副本的 `.wrangler/state/` 中；`db:local` 只能操作本地数据库，不接受远程参数。重复运行迁移通过迁移记录跳过已经执行的文件。

## 2. 在自己的 ChatGPT 账号里创建新站点

使用自己有 Sites 功能的账号，把仓库地址交给 ChatGPT：

> 请从这个 Rally 仓库创建一个全新的 Site。站点放在我的账号下，使用全新项目 ID、全新 DB 和登录配置。不要复用任何已有 Rally 的站点或数据库。按 docs/DEPLOY.zh-CN.md 配置管理员并部署。

负责部署的 Sites 工作流应当：

1. 在新账号/工作区创建新的 Site，保留工具返回的真实新项目 ID。
2. 将这个**新 ID** 写入新副本的 `.openai/hosting.json`。保留 `d1: "DB"`，不要填写旧数据库的 ID。
3. 使用当前 Sites 工具的构建与发布流程，由平台为新项目提供独立数据库和登录网关，并应用本仓库的 schema migrations。
4. 先验证新站点数据为空、登录后权限正确，再把新网址发给新群。

本仓库不自带能创建 ChatGPT Site 的通用 API 密钥或部署令牌；不能只靠运行 setup 就在任何账号发布。需要对方账号具备 Sites 和相应权限。生成的网址由平台分配，不包含对原作者账号、Space 或旧站点的依赖。

如果希望放进 Space，就选择**对方自己的 Space**。如何关联 Site 与 Space 由对方当前的 ChatGPT 界面和 Sites 能力决定，不要把原作者的 Space 当作必需依赖。

## 3. 上线后检查

- 第一次打开，应该没有其他群的场次或姓名。
- 新管理员登录后能管理整个板；其他用户不能越权管理姓名绑定。
- 建一个未来的测试场次，人数上限设为 2。
- 用两个账号报名，再用第三个账号候补；有人退出后，第三个人自动补位。
- 代加一位球友，名字旁有 `(by xxx)`，代加人能删除。
- WhatsApp 分享链接必须回到**新站点自身**。今天提醒和空位列表不重复列出同一场次。

所有测试使用新实例自己创建的数据。不要复制旧站点数据库来测试。

## 4. 更新自己的实例

保留本群的项目 ID、管理员配置、数据库绑定和登录设置。合入代码更新时不要用仓库的空模板覆盖实例配置；不要执行删除、清空或重新导入数据。新 schema migrations 由本实例发布流程处理。

发布通用源码时，另建发布副本移除实例配置，并运行 `npm run check:export`。不要在现有生产实例上运行清理脚本。

## 已知边界

- 当前使用 America/Los_Angeles（Pacific）时间；跨时区群应先统一修改时间计算和界面文案。
- 公开板展示玩家输入的显示名和场次；管理员应向群友说明这个可见范围。
- WhatsApp 是准备分享文案，由使用者选群并发送，不会自动私信。
- 这个版本没有公开 ChatGPT 插件、聊天报名 MCP 或真正的球场预订接口。
- 不建议直接把 Worker 部署到任意普通主机：生产登录依赖 Sites 的可信身份网关。自行托管需要另行实现并验证 OAuth/身份验证，不能相信公网用户传来的身份头。
